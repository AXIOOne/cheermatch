- Portal branding: use one shared CDN logo pointer for default portal imagery and derive the favicon from that source. Why: keep admin, judge, coach, and sign-in branding consistent.

- Use the `font-heading`/`font-body` Tailwind utilities for portal typography instead of inline font-family declarations. Why: the branding fonts (Zilla Slab headings, Roboto body) are defined once in tailwind.config.ts so every surface stays on-brand.
- Built-in email HTML lives only in supabase/functions/_shared/email-layouts.ts (pure TS); edge functions and the admin Email Templates previews both import it. Why: previews always match what is actually sent.
- Email logo assets use an absolute public URL derived from the pointer stored beside the shared email layouts. Why: email clients need absolute URLs and deployed edge functions must not import files outside their shared directory.
- Judge scoring uses equal desktop columns with the current-team scores scrolling inside the video-defined row height; mobile stacks naturally. Why: wider scoring fields stay aligned with the video without content stretching the row.
- Dropbox video export runs through the admin-only dropbox-export function using Dropbox save_url (cloud-to-cloud); the refresh token lives in a service-only table and file naming lives in supabase/functions/_shared/dropbox-naming.ts. Why: large videos never pass through the browser and the token is never exposed to clients.
- Registration video progress is derived by the shared registration-video-progress helper from the latest active submission and non-voided capture attempts; approval remains authoritative through assignment/scoring. Why: table colors reflect existing capture records without changing workflow state.
- Help screenshots (webp) and screen recordings (H.264 mp4 + webp poster) live in public/help/{admin,judge}/ and are referenced from src/content/help/*-topics.ts via image/video blocks; admin and judge topics stay in separate files. Why: each role's Help only shows what that role can access, and media updates need no code changes.
- Verbal judge critiques: audio lives in the private verbal-critiques bucket under {judge_id}/, one verbal_critiques row per score; coaches get them only via the get_verbal_critiques(token) RPC and signed URLs. Why: per-event opt-in, judges own their takes, coach access stays token-gated.
- Event window/cutoff datetime inputs are read and saved in the event's time_zone via src/lib/datetime-local.ts. Why: times stay correct regardless of the admin's computer time zone.
- Whole-panel admin overrides are identified by the database-stamped scores.admin_saved_by, not by another judge's submission. Why: section co-judges must not lock each other out while admin saves remain authoritative.
- Scoresheet SENT badges use service-written scoresheet_email_receipts, never review-token existence. Why: generating a link does not prove an email was accepted.
- Coach performance details use the token-gated get_coach_performance RPC and respect template comment visibility. Why: review videos and submitted scores remain available after the request cutoff without public table access.
- Local capture records distinguish server-reserved attempts from offline/legacy footage; reconciliation removes only known server attempts. Why: missing server rows must not destroy unsynced recordings, while explicit resets still release known attempts.
- Manual upload team eligibility depends on actual video presence, not pending placeholder existence. Why: failed uploads can retry using the existing placeholder.
- Registered-team CSV export uses the table's filtered/sorted rows and shared status labels, with formula-safe CSV encoding. Why: downloaded status matches the visible table without duplicating status rules.
- Admin scoring resolves assignments against the submission team's division and optional level, and names panels from that team's template sections/panels. Why: event-wide panel IDs are reused across divisions with different judges and responsibilities.
